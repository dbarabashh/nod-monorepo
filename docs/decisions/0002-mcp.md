# 0002: Letting AI assistants read meetings over MCP

- Status: accepted
- Scope: `packages/core/src/mcp`, `apps/desktop/src/main/mcp`, `apps/desktop/src/renderer/features/assistants`

## Context

People want to ask their own AI assistant (Claude, ChatGPT, Qwen, Kimi, a
local model) about their meetings. Building one integration per assistant
doesn't scale, and the rules in `.agents/rules/local-first.md` still hold:
meetings stay on the device, content goes to a third party only when the user
enables it, and the destination is visible.

The Model Context Protocol (MCP) is the common way assistants reach outside
data. Desktop assistants start an MCP server as a program and talk to it over
stdin and stdout; other tools connect to an HTTP address.

## Decision

Nod is an MCP server, off until the user turns it on in Settings → AI
assistants.

- **One endpoint, loopback only.** The app serves MCP's HTTP transport on
  `127.0.0.1` (port 47823). It answers only a `Host` of `127.0.0.1:<port>`
  and refuses any request with an `Origin`, so a web page can't reach it by
  rebinding a domain name. Requests are capped at 1 MB and 20 messages,
  connections at 16, and slow requests time out after 10 seconds. Each
  assistant may call tools 60 times a minute, counting every call in a batch.
- **Programs bridge to it.** `Nod --mcp-stdio` relays stdin and stdout to that
  endpoint, so assistants that start a program need no runtime of their own.
  The bridge never opens the meetings; it skips the single-instance lock, uses
  its own browser profile, and exits when its input ends. The key never
  leaves the bridge: for each request it fetches a one-time challenge, sends
  the key's id (the start of its SHA-256 hash) and an HMAC over the challenge
  and the body keyed by the whole hash, and checks the server's HMAC over its
  reply. Request and reply HMACs carry different labels. Another user's
  program squatting on the port, even mid-session after Nod restarts, gets
  nothing it can replay or use, and can't pass off a reply as Nod's.
- **A key per assistant.** Connecting an assistant creates a random key, shown
  once; only its SHA-256 hash is stored. The settings (`mcp.bin`) are sealed
  with the OS keychain, like the data key, so a program that can write files
  can't add an assistant of its own; the stored hash signs requests, so it is
  as valuable as the key. A file that doesn't open is moved aside and reads as
  off, and Settings says so; when the keychain itself isn't available yet
  (a locked keyring), the file is left alone and nothing can change until
  Nod restarts with it. Each request is matched against the
  current list, so disconnecting stops it at once, even if saving that fails.
- **Read only, with permissions.** The tools are `list_meetings`,
  `search_meetings`, `get_meeting` and `list_folders`. Names, dates and
  folders are always visible (a name may come from the summary model);
  summaries and transcripts only when allowed for that assistant, and search
  looks only in what it may read. Long transcripts come in pages.
- **Visible use.** Settings shows when each assistant last read and a list of
  recent reads, kept in memory.
- **No SDK.** The server implements the part of MCP it needs (initialize,
  ping, tools/list, tools/call; JSON responses, no streaming) instead of
  adding a dependency.

## Consequences

- A cloud assistant sends what it reads to its provider. Settings says so;
  an assistant running on the same computer keeps it there.
- ChatGPT only connects to internet addresses, which Nod doesn't offer: that
  would need a public endpoint seeing plaintext, which the sync relay is
  designed never to do.
- A key in an assistant's settings file can be read by other programs running
  as the same user. Keys are per assistant, read only and can be disconnected.
- A program squatting on the port while Nod is closed still sees what the
  assistant asks (search words, meeting ids), though never a key or a reply
  it could pass off as Nod's.
- Tools that connect to the address directly send their key as a bearer
  token, so on a computer shared with other users the program setup is the
  safer one.
- The program setup names the app's own path. On Windows that path changes
  with each update, so the assistant has to be set up again afterwards, and
  the bridge depends on Electron passing piped stdin to a GUI build; both
  have to be checked there before Windows is called supported.
