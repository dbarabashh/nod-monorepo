# 0001: Device sync with an Automerge document per meeting

- Status: accepted
- Scope: `packages/core/src/meetings`, `packages/core/src/sync`, `apps/desktop/src/main/meetings`, `apps/desktop/src/main/sync`

## Context

The app keeps meetings on the user's devices, encrypted at rest, and must let
one person use it on several devices (desktop first, phones later) without a
server that can read their data. The rules in `.agents/rules/local-first.md`
set the constraints:

- content leaves a device only as ciphertext the transport cannot read;
- concurrent edits merge without silently dropping data, never by blind
  last-write-wins;
- deletion propagates to every device;
- the data model is platform-neutral and exportable to open formats;
- audio is never stored, so nothing about sync involves audio.

A meeting is mostly append-only and written by one device: the recording
device adds segments and transcript lines. Real conflicts only arise where a
person edits: the summary, a transcript line, the title, finishing, deleting.

## Options considered

1. **Plain files plus a user's file-sync service, merged with diff3** (the way
   some local-first Markdown apps do it). Simple and transparent, but the
   files would be readable by the provider, the merge works on text rather
   than on the meeting's structure, and iCloud or git are not available or
   practical on every platform we target.
2. **Our own CRDT for each field.** Small, but correct text CRDTs are hard and
   this is exactly where data gets lost quietly.
3. **A CRDT library document per meeting.** Measured with a two-hour meeting
   (1,200 lines, about 20,000 words, 206 KB as JSON), building it in 600
   batches the way transcription does, then editing the summary and a line
   on two forks and merging:

   |                  | Automerge 3.5 | Loro 1.16               |
   | ---------------- | ------------- | ----------------------- |
   | snapshot         | 84 KB         | 272 KB (192 KB gzipped) |
   | open             | 61 ms         | 14 ms                   |
   | merge            | 4.5 ms        | 6.5 ms                  |
   | change per batch | 578 B         | 444 B                   |
   | WASM             | 3.6 MB        | 3.4 MB                  |

   Both merged both edits correctly. Yjs was not measured: its strengths are
   bindings to editors we don't use.

## Decision

Each meeting is one **Automerge** document. Automerge has a documented, stable
binary format with implementations for JavaScript, Rust, Swift and the JVM, a
three times smaller snapshot here, and a long track record. Opening in 61 ms
is acceptable for one meeting at a time.

### Document shape (schema 1)

```
{
  schema: 1,
  id: string,
  title: string,                 // whole value: the starting or the user's name
  titleEdited: boolean,          // the user renamed it
  generatedTitle: string | null, // whole value: the summary model's name
  folder?: string | null,        // whole value: the meeting folder's name
  segments: [{ startedAt, endedAt }],
  finishedAt: number | null,
  lines: { [lineId]: { speaker, startMs, endMs, text } },  // text is a text CRDT
  summary: string,               // text CRDT, '' when there is none
  summaryEdited: boolean,
  deletedAt: number | null
}
```

- Transcript lines live in a map keyed by a random line id, so lines appended
  on different devices never collide and order comes from `startMs`.
- Text fields merge character by character. Scalars (`finishedAt`,
  `summaryEdited`, segment ends) are only ever set by one device in practice;
  Automerge keeps concurrent values and picks the same winner everywhere.
- Names are whole values, not text: two devices naming a meeting at once keep
  one of the names instead of interleaving their letters. The model writes only
  `generatedTitle`, so it never competes with the user's name; the name shown
  is the user's if they renamed it, else the generated one, else the starting
  one. Documents from before these fields read them as unset, and a title
  stored as text is read as it is and becomes a whole value on the next edit.
- A meeting folder is the name a meeting is filed under, not a record of its
  own. It exists while a meeting is in it, so creating one is filing a meeting
  there, and there is no empty folder to sync. Like a name, it is one choice:
  two devices filing a meeting at once keep one of the two, the same on every
  device. Documents from before folders have no such field and read as unfiled,
  and devices that predate it carry the field along untouched. A value this
  version can't use reads as unfiled rather than hiding the meeting.
- The summary is always text, so a summary written by the model on one device
  and typed or cleared on another merges instead of one side replacing the
  other.
- The plain `Meeting` type stays the app's model. A save writes only the
  difference between the meeting the caller last saw and the one it saves, so
  a caller holding an older copy can't undo what arrived from another device
  meanwhile. A projection reads a `Meeting` back, so the meeting logic and its
  tests don't depend on Automerge.
- A merge from another device is adopted by the store and shown by the
  recorder in the same step, before anything else can save the meeting.

### Deletion

Deleting sets `deletedAt`. Any device that sees `deletedAt` replaces its copy
with a tombstone document that holds only `{ schema, id, deletedAt }` and no
history, and rewrites what it publishes. Deletion wins over concurrent edits,
and a deleted meeting's text does not survive in any device's history once
every device has seen the tombstone.

### Local storage

Each meeting is one file, `meetings/<id>.bin`, holding the Automerge document
encrypted with AES-256-GCM under a random local data key. Both apps keep
them with the same store (`packages/core/src/meetings/store.ts`) over their
own filesystem. The data key is
stored wrapped by the OS keychain (`safeStorage`). Nothing is
saved or merged until the stored meetings were read, and sync doesn't start
if they couldn't be. A file that can't be read is never overwritten; a valid
copy from another device replaces it and the damaged file is kept beside it.

### Transport

Sync goes through a transport that stores opaque files and never merges:

- every device writes only its own files:
  `<vault>/devices/<device>/meetings/<meeting>.bin`, so a file-sync service never sees two
  writers on one file and never creates conflict copies;
- a device reads every other device's files and merges them with Automerge;
- a device writes a copy only when the vault lacks that version: a meeting it
  only received, still held by another device's listed file, isn't written
  back, so a new device writes nothing to pair. Once a device has a copy of
  its own it keeps it current (a deleted meeting's text never stays behind),
  and it writes one when it has a change or the other copy disappears. Which
  version it last wrote, and which version tag the place gave that copy (at
  the write, or in the next listing for a relay that doesn't say), are
  remembered across restarts (hashes and tags only), so starting the app
  doesn't write every meeting again. A copy listed under another tag, or
  missing from the listing, is read back first: one that still holds this
  version is left alone (a listing that lags, a folder that re-stamps
  files), one the place changed behind the device's back (a relay or folder
  restored from a backup, a transport that serves an older file) or lost is
  written again at the next round. A listed tag is taken as the copy's own
  when the place named none at the write, or once two listings in a row
  show it, so a lagging listing can't hand a copy the tag of what it
  replaced, and a folder that re-stamped every file is read back twice, not
  every round. A device that never saw a
  deletion can't tell a withheld tombstone from a live meeting; what this
  closes is the window in which an old copy stays on the place after its
  device noticed;
- a file that can't be read as listed (not sealed for this vault, damaged,
  or over 16 MiB, far above any meeting) is fetched once per listed version
  and reported until the place lists another version of it, so a planted
  file costs one download rather than one per round; a device never writes
  a copy that large either, and reports that meeting instead;
- a full quota ends the round's writes, and reading goes on; a rate limit
  (the place's own, or one in front of it) ends the round, and the device
  makes no request at all, not even the listing, until the wait the place
  named has passed (a minute when it named none, five seconds at least, ten
  minutes at most), since asking sooner only keeps the limit tripped; the
  relay names the time left in the hour for its own hourly limits, and
  marks its limit on writes, which ends the round's writes only;
- a device also reads its own copy of a meeting it no longer holds (it
  started over, or was reinstalled with the same id), since that copy may be
  the only one;
- a file is the full document encrypted with the vault's file key (AES-256-GCM,
  the vault, device and meeting ids bound as associated data). The first byte
  names the format version; version 1 binds only the context, as every file
  already written does, and any later version must bind its version byte as
  well, so a file can never be opened as a version it wasn't sealed with.

Two transports share this layout:

- **folder**: any folder the user already syncs (iCloud Drive, Dropbox,
  Syncthing, a network drive), under `nod-sync/<vault>/`;
- **relay**: a small self-hostable HTTP server that stores the same files per
  vault and authenticates writers with a token derived from the vault key.

The transport sees vault and device ids, file sizes and times, never content.

### Keys and the recovery phrase

A device gets its vault key in onboarding, before anything syncs, or later in
Settings if it was set up before this existed:

- **New to the app**: the device creates a random 256-bit vault key and shows
  it as a 24-word BIP39 phrase, which the user writes down.
- **Already uses the app**: the user enters the phrase from another device,
  and this device takes the same key.

The vault id is derived from the key: the relay token is
HMAC-SHA256(key, `nod:relay-token`) as hex, and the id is the first 16 bytes
of SHA-256 of that token, as hex. So the 24 words are all a device needs to
find its vault on any folder or relay, and a relay can check that whoever
registers a vault id holds the key it is named after; nobody can claim an id
they have seen first. Neither value reveals the key, but the id is the same in
every folder and relay a vault uses, so it links them. Two people sharing one
folder or relay never mix, because their keys name different vaults.

Entering another phrase on a device that already has one switches it to that
vault: it removes what it published to its old vault and publishes its
meetings to the new one.

The page is untrusted, and a script in it may get hold of a real click. So
the page never sees the phrase, and what shows a key, puts one on the device
or sends meetings somewhere new goes through a dialog main draws, which a page
script can't read or click through. Creating a phrase needs none, since main
makes the key from random bytes, and a folder is chosen in the system picker.

- showing the phrase: main shows the 24 words and the vault code (the first
  64 bits of the vault id), records "written down" only from that dialog, and
  shows it at most once every ten seconds, since a screen may be shared;
- entering a phrase (the first time, to switch, or to replace a key that
  can't be read): main shows the words it received and their vault code, so
  words the page swapped for its own don't match the paper or another
  device's dialog; finding other words with the same code would take about
  2^64 tries;
- connecting any relay (the build's own included), named by its host, and
  stopping sync.

While a dialog or the folder picker is open nothing else about sync can
change. After a Cancel the next request waits ten seconds, and each further
Cancel doubles the wait up to five minutes; only a confirmed change resets
it. So a script can't keep reopening a dialog on every later click until the
user gives in. The phrase dialog also
says whether any device syncs with the words yet, which catches the one
mistyped word in 256 that still passes the 8-bit checksum, and warns when the
old place can't be reached so copies would stay behind. A relay address may
hold only a host and a short, plain path, never a login, query, fragment or
long path that could carry data to whoever runs it.

The key is stored wrapped by `safeStorage` in the same file as the settings
tied to it, written in one atomic step, one save at a time. A key that can't
be read (a locked keyring, a damaged file) is never replaced silently: sync
pauses until it can be read, or until the user enters their phrase and
confirms replacing it. The page can ask for any of this only during a user's
click. Devices that were lost keep their published, encrypted files until they are
forgotten (see Forgetting a device).

### Subkeys and changing the phrase

The phrase encodes the root key, and nothing uses the root key directly. The
file key that seals meetings is HKDF-SHA256 of the root key with salt
`nod:vault`, info `files` and 32 bytes of output; the relay token and vault id
come from their own derivation above. A slow password hash would add nothing,
since the phrase carries 256 random bits.

The phrase can be changed, for when it may have leaked or a device was lost.
The device makes a new root key and saves it first, so it can't be lost; then
it removes its own files from the old vault, leaves a notice there
(`devices/<device>/closed.json`: the JSON `{"closedAt": <ms>}` sealed with
AES-256-GCM under the old file key, with `nod:closed:<vault>:<device>` as
associated data, so no folder service or relay can forge one), and asks the
user to write the new phrase down. The user
enters the new phrase by hand on each device they keep, the same way a device
is added, comparing the vault code. A lost or removed device never gets it:
there is nothing to hand it over.

A device that finds the notice stops syncing through the old vault for good,
even if the notice later disappears, and asks for the new phrase; it can also
make a new phrase of its own or stop syncing. A notice it can't read holds
sync back rather than risk writing into a closed vault.

Until a kept device has the new phrase it keeps syncing through the old vault,
and what it syncs there can be read with the old phrase. Whoever holds the old
phrase or the relay token can keep deleting the notice, so a kept device may
never notice the change by itself: the new phrase has to be entered on each
kept device, soon. A holder of the old phrase can also post a notice, which
only stops sync and asks for a phrase; it never moves a device anywhere. A
lost device keeps what it already had: nothing can take that back.

This goes further than Anytype, whose key can't be changed at all. An earlier
design handed the new key to the kept devices automatically, sealed to device
keys; a device that still held the old phrase could forge the device records
and notices that rested on it, so it was dropped in favour of entering the
phrase by hand.

Where meetings travel is chosen separately and can change without changing the
key. A build can name a default relay (`NOD_RELAY_URL` at build time), which
Settings offers as the first choice; nothing goes to it until the user turns
it on and confirms its host. Being offline never blocks setup: the key is saved at once, and every
sync round tries to reach the folder or relay again. Stopping sync while the
place can't be reached is only possible after the user agrees that copies may
stay there.

### Cryptography

All primitives come from audited libraries and live in `packages/core/src/crypto`, so
every client runs the same code: AES-256-GCM from `@noble/ciphers`, SHA-256,
HMAC and HKDF from `@noble/hashes`, and BIP39 from `@scure/bip39`. The formats
match what OpenSSL produces for the same inputs, and a test in
`apps/desktop/src/main/security` checks files and keys against `node:crypto`. The app
writes no cryptographic primitive of its own; it only composes these into the
file format and key derivation described here.

### Pairing a phone by QR code

A phone can't reach a folder on the computer, so it syncs only through a
relay, and it joins by scanning a code instead of typing 24 words. Pairing
needs the phone on the computer's own network; after that it syncs through
the relay from anywhere.

The code never holds the vault key. It is
`nod-pair:v3:<secret, base64url>:<port>:<addresses>`: a random 32-byte secret
made for this one pairing, and the private or link-local IPv4 addresses and
port where the computer listens while the code is shown
(`packages/core/src/sync/pairing.ts`). The phone asks the computer there for
the offer, proving it holds the secret with HMAC-SHA256(secret,
`nod:pair-request:<address>:<port>`), a proof made for that one address, so
one caught by whatever answers at a wrong address in the code can't be shown
at the right one. The computer then asks its user, in a dialog main draws
that names the asking address, and answers 202 (holding each ask a few
seconds, and naming the asker's address in the body, which the phone shows
next to "Choose Pair on your computer") until they decide: Pair sends the
root key and relay sealed with AES-256-GCM under HKDF-SHA256(secret, salt
`nod:pair`, info `offer`), once, and the computer stops listening and closes
the code; Don't pair answers 403 and closes too, as does a dialog that fails.
The phone gives up waiting with the code's three-minute window and says so.
While one phone is being asked about, no other address gets anything, and
the listener outlives the code window until the user has answered and the
phone has collected the offer or the refusal, or ten seconds passed. Only requests to the
addresses in the code count; anything else gets the same 404, and twenty
wrong tries before any phone is being asked about close the port and the
code. Once the offer is taken the computer says which address on the network
took it, so a code taken by someone else shows up at once and the user can
change the phrase. So a photo of the code is useless away from that network,
after the first use, or once the window is closed; and someone who asks with
it before the user's own phone does gets the key only if the user chooses
Pair for an address their phone doesn't show, which the dialog tells them to
check. Nothing that answers on the network can hand the phone a vault of its
own, since the offer must open with the secret. The phone reads the
code as untrusted input: anything else, or an address outside the private
ranges, is refused before it connects anywhere. The relay in the offer must
be `https:` and named, not an IP address (loopback stays for the simulator).

Main draws the code in a window of its own that has no preload, runs no
JavaScript and uses a session kept in memory, served under an opaque
`nod-pairing://code/` address, so the untrusted app page never sees the
secret. The window asks macOS and Windows to keep it out of screenshots and
shared screens (not every capture API honours that) and says on Linux that it
can be captured; it closes when the phone took the offer, or after three
minutes. Showing it counts as an open question, and it shares the phrase's
ten-second interval, counted from when it closed.

The phone stores the key and its device id with `expo-secure-store`,
available after the first unlock and never moved to another device; meetings
are files sealed with a local key kept the same way, and Android backups are
off. Right after pairing it syncs, and the list fills as meetings arrive. A
phone that already holds meetings first shows the vault it was handed and
asks, since its meetings join it. It never replaces a vault it still syncs
with by another one; the user stops syncing first, which also removes its
copies from the relay and is the way out of sync settings that can't be read.
Meetings whose local key is missing are kept aside only when the user starts
over, and a new key goes in a new keychain entry. iOS still includes those
files in backups: excluding them needs a native module. Android refuses
plain HTTP by default and can't allow it for private ranges only, so the app
allows it (`plugins/with-local-pairing.js`); relays stay `https:`-only in
`@nod/core`, so the only plain request is the sealed pairing offer.

### Forgetting a device

A device that was lost, reset or reinstalled leaves its copies in the vault.
Settings → Sync lists the other devices by what they put there (meetings,
last change) and forgets one after a sync round and a dialog main draws. Its files
are removed only if this device has merged every one of them at the version
the vault lists, and only after this device wrote its own copy of any meeting
only that device held, so the vault never lacks one. Forgetting is cleanup, not revocation: a device still in
use writes its copies again as its meetings change, and shutting a lost one
out is changing the phrase.

### Relay

The relay keeps the same layout under a vault id. The first device to connect
registers the vault with its token, which must hash to the vault id, and every
device with the same key derives the same token; the relay stores a hash of
it and requires the token for every file.

A hosted relay runs the same file API as a Vercel Function over private blob
storage (`apps/desktop/relay/vercel`). It stores no secrets, since a vault id is the hash of
its token, keeps a per-vault index so polling costs one small read, and limits
file size, vault size, writes per hour and new vaults per hour.

Stopping sync on a device removes its published meetings but keeps its
tombstones, so a deletion still reaches devices that haven't seen it. The key
stays on the device, so sync can be turned on again with the same phrase.

## Consequences

- Dependencies that ship in the app: `@automerge/automerge` (MIT, 3.6 MB
  WASM) and the audited `@noble/ciphers`, `@noble/hashes` and
  `@scure/bip39` (MIT, no dependencies beyond each other, no install scripts).
  All are platform-neutral, so `packages/core` may use them.
- Saving a meeting writes only that meeting.
- Exports stay JSON and Markdown; the Automerge file is an internal format with
  a public specification.
- Not covered yet: sharing a meeting with another person, which needs
  per-meeting keys.
- Meeting files moved from the root key to the file key without a format
  marker; no build with the earlier format shipped, and devices publish their
  meetings again under the new key on their first round.
