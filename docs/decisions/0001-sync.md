# 0001: Device sync with an Automerge document per meeting

- Status: accepted
- Scope: `src/core/meetings`, `src/core/sync`, `src/main/meetings`, `src/main/sync`

## Context

The app keeps meetings on the user's devices, encrypted at rest, and must let
one person use it on several devices (desktop first, phones later) without a
server that can read their data. The rules in `.agents/rules/local-first.md`
set the constraints:

- content leaves a device only as ciphertext the transport cannot read;
- concurrent edits merge without silently dropping data, never by blind
  last-write-wins;
- deletion propagates to every device;
- the data model is platform-neutral and exportable to open formats;
- audio is never stored, so nothing about sync involves audio.

A meeting is mostly append-only and written by one device: the recording
device adds segments and transcript lines. Real conflicts only arise where a
person edits: the summary, a transcript line, the title, finishing, deleting.

## Options considered

1. **Plain files plus a user's file-sync service, merged with diff3** (the way
   some local-first Markdown apps do it). Simple and transparent, but the
   files would be readable by the provider, the merge works on text rather
   than on the meeting's structure, and iCloud or git are not available or
   practical on every platform we target.
2. **Our own CRDT for each field.** Small, but correct text CRDTs are hard and
   this is exactly where data gets lost quietly.
3. **A CRDT library document per meeting.** Measured with a two-hour meeting
   (1,200 lines, about 20,000 words, 206 KB as JSON), building it in 600
   batches the way transcription does, then editing the summary and a line
   on two forks and merging:

   |                  | Automerge 3.5 | Loro 1.16               |
   | ---------------- | ------------- | ----------------------- |
   | snapshot         | 84 KB         | 272 KB (192 KB gzipped) |
   | open             | 61 ms         | 14 ms                   |
   | merge            | 4.5 ms        | 6.5 ms                  |
   | change per batch | 578 B         | 444 B                   |
   | WASM             | 3.6 MB        | 3.4 MB                  |

   Both merged both edits correctly. Yjs was not measured: its strengths are
   bindings to editors we don't use.

## Decision

Each meeting is one **Automerge** document. Automerge has a documented, stable
binary format with implementations for JavaScript, Rust, Swift and the JVM, a
three times smaller snapshot here, and a long track record. Opening in 61 ms
is acceptable for one meeting at a time.

### Document shape (schema 1)

```
{
  schema: 1,
  id: string,
  title: string,                 // text CRDT
  segments: [{ startedAt, endedAt }],
  finishedAt: number | null,
  lines: { [lineId]: { speaker, startMs, endMs, text } },  // text is a text CRDT
  summary: string,               // text CRDT, '' when there is none
  summaryEdited: boolean,
  deletedAt: number | null
}
```

- Transcript lines live in a map keyed by a random line id, so lines appended
  on different devices never collide and order comes from `startMs`.
- Text fields merge character by character. Scalars (`finishedAt`,
  `summaryEdited`, segment ends) are only ever set by one device in practice;
  Automerge keeps concurrent values and picks the same winner everywhere.
- The summary is always text, so a summary written by the model on one device
  and typed or cleared on another merges instead of one side replacing the
  other.
- The plain `Meeting` type stays the app's model. A save writes only the
  difference between the meeting the caller last saw and the one it saves, so
  a caller holding an older copy can't undo what arrived from another device
  meanwhile. A projection reads a `Meeting` back, so the meeting logic and its
  tests don't depend on Automerge.
- A merge from another device is adopted by the store and shown by the
  recorder in the same step, before anything else can save the meeting.

### Deletion

Deleting sets `deletedAt`. Any device that sees `deletedAt` replaces its copy
with a tombstone document that holds only `{ schema, id, deletedAt }` and no
history, and rewrites what it publishes. Deletion wins over concurrent edits,
and a deleted meeting's text does not survive in any device's history once
every device has seen the tombstone.

### Local storage

Each meeting is one file, `meetings/<id>.bin`, holding the Automerge document
encrypted with AES-256-GCM under a random local data key. The data key is
stored wrapped by the OS keychain (`safeStorage`). The previous single
`meetings.bin` is migrated once and deleted after every meeting reads back
from its new file, so a deleted meeting doesn't live on in it. Nothing is
saved or merged until the stored meetings were read, and sync doesn't start
if they couldn't be. A file that can't be read is never overwritten; a valid
copy from another device replaces it and the damaged file is kept beside it.

### Transport

Sync goes through a transport that stores opaque files and never merges:

- every device writes only its own files:
  `<vault>/<device>/<meeting>.bin`, so a file-sync service never sees two
  writers on one file and never creates conflict copies;
- a device reads every other device's files and merges them with Automerge;
- a file is the full document encrypted with the vault key (AES-256-GCM, the
  vault, device and meeting ids bound as associated data).

Two transports share this layout:

- **folder**: any folder the user already syncs (iCloud Drive, Dropbox,
  Syncthing, a network drive);
- **relay**: a small self-hostable HTTP server that stores the same files per
  vault and authenticates writers with a token derived from the vault key.

The transport sees random ids, file sizes and times, never content.

### Keys and pairing

The first device creates a vault: a random id and a 256-bit vault key, stored
wrapped by `safeStorage`. Another device joins through the transport itself,
in `pairing/<request>/`:

1. **request**: the new device publishes a hash of a fresh X25519 public key;
2. **offer**: the existing device publishes its own fresh public key;
3. **reveal**: the new device publishes its public key, and the existing device
   checks it against the hash;
4. both devices show a six-digit code derived from both public keys; the user
   confirms on the new device and allows on the existing one only if the codes
   match;
5. **grant**: the existing device publishes the vault id and key, encrypted
   with a key derived from the X25519 shared secret.

Each side pins what it read the first time: the existing device its offer,
the commitment and the revealed key; the new device the offer. A later change
ends the request instead of being used, the approval names the code the user
saw and is sealed only to the pinned key, and the new device only takes a
grant after its own user confirmed. When several devices of the vault are
running, the first to post an offer answers and the others leave the request
alone. Each device answers a few requests at a time and drops one whose key
was not revealed within ten minutes.

A transport that swaps keys gets different codes on the two screens. The hash
in step 1 stops it from searching for a swapped key that happens to give the
same code: it must commit to a key before it learns the other device's key.
Desktops have no camera, so the code is compared by eye rather than scanned.

### Recovery phrase

The vault key can be shown as a 24-word BIP39 phrase on any device that
syncs. A new device restores from the phrase and the folder or relay (plus the
vault id for a relay). The phrase is checked against the vault before anything
is saved: a check file sealed with the vault key, written when the vault is
created, must open with it, and a relay must accept the token derived from
it, so a phrase from another vault is refused rather than starting an empty
sync. The renderer gets the phrase only on the user's click, and the
transport can never recover it. Devices that were lost keep their published,
encrypted files until a way to forget a device exists.

### Cryptography

All primitives come from audited libraries and live in `src/core/crypto`, so
every client runs the same code: AES-256-GCM from `@noble/ciphers`, X25519 from
`@noble/curves`, SHA-256, HMAC and HKDF from `@noble/hashes`, and BIP39 from
`@scure/bip39`. The formats match what OpenSSL produces for the same inputs, and
a test in `src/main/security` checks files and keys against `node:crypto`. The
app writes no cryptographic primitive of its own; it only composes these into
the file format, the pairing protocol and key derivation described here.

### Relay

The relay keeps the same layout under a vault id. The first device registers
the vault with a token derived from the vault key; the relay stores a hash of
it and requires the token for everything except the pairing area. There, a
device without the token may only post the request and a reveal whose key
matches the request's commitment, and read the answers; offers, grants and
deletions need the token. Pairing files are
small, written once, limited to sixteen open requests per vault, and
forgotten after a day.

Leaving sync removes this device's published meetings but keeps its
tombstones, so a deletion still reaches devices that haven't seen it.

## Consequences

- Dependencies that ship in the app: `@automerge/automerge` (MIT, 3.6 MB
  WASM) and the audited `@noble/ciphers`, `@noble/curves`, `@noble/hashes` and
  `@scure/bip39` (MIT, no dependencies beyond each other, no install scripts).
  All are platform-neutral, so `src/core` may use them.
- Saving a meeting writes only that meeting.
- Exports stay JSON and Markdown; the Automerge file is an internal format with
  a public specification.
- Not covered yet: sharing a meeting with another person, which needs
  per-meeting keys, and key rotation after removing a device.
